## Independent review corrections

Three agents implemented and cross-reviewed browser/authentication coverage,
background exports, and capacity/recovery. Independent passes also examined
the root regex, analytics, and report-library changes. Concrete corrections
included excessive retained rule-preview bodies, eligibility checks after size
checks, unapplied search fields surviving Clear, a missing model index binding,
orphaned workload descendants, unnecessary Celery result subscriptions after
broker restart, stalled export publication, and oversized ready-export
reservations. Download preparation now uses anonymous files owned by the
response, so API process death releases plaintext scratch without a named-file
janitor. These corrections have focused regression coverage.

The Celery fault was reproduced with the installed client: result-consumer
reconnection could deadlock while an unused result was finalized. Application
tables already owned progress, so registered tasks and named producers now
ignore those results. The recovery drill verifies publication resumes without
restarting the producer. Background-export publication separately uses bounded
Redis socket operations and no library retries; durable dispatch owns retries.
This is not a wall-clock guarantee against a continuously trickling Redis peer.

## Deployment and operating implications

Upgrade API, workers, and Beat together after migration `0087_async_exports` and
`0088_report_library_indexes`. The latter builds report keyset/title indexes and
an AI-failure partial index; account for index-build I/O and write locks on a
large retained database. Existing synchronous exports and offset report API
clients remain compatible.

Background exports use the processing and maintenance queues, plus Beat. Their
default deadline is one hour and retention is one day from acceptance. Current
byte/item limits still apply. Retain required application encryption keys until
jobs expire; credential expiry or logout can invalidate a job. Admission tracks
encrypted retained data, while temporary generation storage, PostgreSQL WAL,
MVCC cleanup, backups, and concurrent processes require separate disk planning.
See the [configuration reference](../reference/configuration.md) and
[background-export runbook](../reference/background-exports.md).
