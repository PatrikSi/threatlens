# ThreatLens 2.1.0

This release expands team intelligence, reviewed indicator publication, AI
provider governance, signed automation and scoped MCP access. It also preserves
accepted AI work through recovery and strengthens retained evidence and
publication handling-label checks.

These notes describe the 2.1.0 source candidate. A public `v2.1.0` tag and its
container references become available after the release workflow passes. Use a
published immutable release or commit reference for a controlled deployment.

The versioned OpenAPI contract SHA-256 is
`a608ae21656a8d50f83919e01a16751720c1199a7f4cd552465770bd3df16aaa`.

## Main changes

- [Team intelligence](../pages/teams.md) adds evidence-backed assessments,
  shared hunt queues, analyst claims, review, priorities, deadlines and saved
  views. Evidence review is pinned to its source and assessment revisions.
- [Indicator intelligence](../pages/indicator-conditions.md) records normalized
  observables and provenance, current source-reported AI roles, analyst verdicts
  and suppression. Conditions can require several predicates to match the same
  indicator rather than unrelated indicators in an article.
- [Reviewed STIX/MISP publications](../pages/reviewed-publications.md) retain
  approved evidence and handling labels, stable identities, consumer revisions
  and withdrawal history. Consumers reconcile authorization and acknowledge
  their applied policy revisions.
- [AI governance](../pages/ai-quality-and-coverage.md) adds provider routing,
  shared account admission quotas, bounded section extraction, explicit
  continuation budgets, optional synthesis and provider contract qualification.
  Recovery preserves accepted checkpoints and blocks replay of ambiguous
  provider outcomes. Offline evaluation requires exact case/output revisions
  and named analyst judgments before semantic promotion.
- [Team integrations](../pages/team-integrations.md) support governed AI
  destinations and scoped receiver credentials. Signed durable automation
  snapshots, [execution tracking](../pages/automation-execution.md) and the
  [OpenSearch hunt connector](../pages/opensearch-connector.md) distinguish
  transport delivery, external execution and policy enforcement.
- [SOC webhooks](../pages/intelligence-automation.md) can route on accepted AI
  relevance with current evidence provenance and on completion events.
  Searchable condition/payload controls and permission-aware previews expose
  the retained event revision. Extracted
  article text requires an explicit opt-in: structured automation uses
  `include_article_text`, while request templates opt in by placing
  `{{item.full_text}}` in a body value. Text is limited to supported body fields;
  previews do not send requests.
- [MCP](../pages/mcp.md) offers nine scoped read tools, evidence pagination and
  registered-client OAuth consent with PKCE and resource binding. Existing API
  credentials remain supported within their effective permissions.
- Browser workflows preserve analyst drafts through navigation, viewport
  changes, session-verification outages and polling. Explicit identity/access
  changes retire protected state. The CSS build tooling was updated while
  preserving the existing light/dark themes and component styles.
- Packaging updates the patched Python and OS dependencies recorded in the
  runtime inventories. Source-build contexts exclude local environment files,
  the unused backend developer lock and browser output; release configuration
  comes from the documented build arguments and runtime environment.

## Upgrade from 2.0.x

1. Verify a pre-upgrade PostgreSQL backup and keep its corresponding encryption
   key, environment, Compose definition and exact working image/source
   reference in private storage. Use the
   [recovery tooling](../pages/database-privileges.md) to verify the archive and
   perform a disposable drill. Preserve initialized credentials and volumes.
2. Use the matching 2.1.0 checkout and a published image reference. Keep the
   separate runtime/migration/recovery database identities established in 2.0.
   If the installation still uses one database role, complete the
   [offline cutover](../pages/database-privileges.md#existing-installations-explicit-offline-cutover)
   before these commands. Upgrades from 1.x must also follow the
   [2.0 upgrade requirements](2.0.0.md#upgrade-from-1x).
3. Stop API, Beat and every worker before applying the new schema. Migration
   0123 rewrites the `items` table to populate generated identity digests and
   rebuild indexes, so allow a maintenance window appropriate to the data
   volume. Retained publisher identifiers and URLs are preserved.
4. Apply migrations with the dedicated migration service, then recreate the
   complete API/worker stack using the same image. Mixed old/new API and worker
   processes are unsupported. Retain the dedicated export, maintenance,
   notification and AI workers; the AI queues remain
   `ai,ai-reports-v2,ai-reports-v3`.
5. Check migration completion, service readiness, login, ingestion, processing
   recovery and a synthetic background export. Confirm intended team access,
   publication consumer policy state and webhook settings. Run a fresh backup
   and disposable recovery drill after the upgrade.

After `v2.1.0` and its images are published, the standard Compose upgrade is:

```bash
export THREATLENS_IMAGE_TAG=2.1.0
docker compose pull
docker compose stop --timeout 300 api beat worker worker-ai worker-exports worker-maintenance worker-notifications
docker compose run --rm migrate
docker compose up -d --wait
docker compose ps
```

Use the same environment/Compose selection on every command for a custom or
Portainer installation. Normal API/worker credentials intentionally cannot
perform schema changes. PostgreSQL, Redis and the web proxy can remain running
during the stopped-writer migration; the UI reports the temporary API outage.

## Migration and integration behavior

The 2.1.0 schema advances through migrations `0106`–`0125`. Populated legacy
webhook configuration, encrypted credentials and delivery snapshots are
preserved by the article-text migration.

| Change | Upgrade behavior |
|---|---|
| Item identity indexes (`0123`) | Generated SHA-256 digest columns bound deduplication index entries without truncating publisher identities. Downgrade refuses retained identity fields over 2,000 bytes because the older indexes cannot represent them. |
| Reconciliation progress (`0124`) | Historical reconciliation timestamps become attempt timestamps. A successful-progress timestamp remains empty until actual successful reconciliation; the migration does not invent success. |
| Webhook article text (`0125`) | Structured automation defaults to `include_article_text=false`. Template notifications opt in independently by using `{{item.full_text}}` in body values; the flag does not remove that placeholder. Choose either mechanism deliberately for an authorized destination and inspect the safe preview. |
| External execution and withdrawal | Receiver delivery success does not mean an external hunt executed. Receivers must record execution state and acknowledge the policy revision they actually applied; revoked/changed policy can require reconciliation. |
| Retained labels/evidence | Deleting the original item does not remove a reviewed publication's handling-label obligation. Label archival remains blocked while retained publications or other history reference it. |
| AI evaluation approval | Blank, future, timezone-free or stale review provenance does not qualify a case or output. Changed content requires a new review of the exact revision. |

Rollback is an operator migration or restore procedure. Stop all writers and
honor the existing ownership/publication/digest guards. A refused downgrade
requires retaining the current schema or restoring the verified pre-upgrade
backup with its matching application version; do not truncate retained evidence
to bypass the guards. Restore quarantine deliberately retires machine access
and requires appropriate reconciliation before external automation resumes.

## Qualification and boundaries

The Tailwind 4 CSS toolchain supports Safari 16.4+, Chrome 111+ and Firefox
128+. Existing themes and styles are preserved within that
[supported browser floor](https://tailwindcss.com/docs/upgrade-guide#browser-requirements).

Provider contract checks establish request/response compatibility, evidence
validation and receipt behavior. Semantic model promotion still requires the
named analyst workflow and representative outputs, cost and latency evidence
described in the [AI quality guide](../pages/ai-quality-and-coverage.md).
The checked-in seed package currently has twelve cases awaiting analyst review;
it contains no captured model outputs or semantic promotion evidence. Structured
AI extraction and hunt proposals remain opt-in, as do MCP and OAuth access.

Teams govern collaboration and access within an installation; they do not
provide full tenant isolation for global feeds, providers and resources. Hunt
deadline reminders are in-app. Publication distribution uses pull/reimport and
consumer reconciliation. MCP remains read-only and does not provide dynamic
client registration, refresh tokens, prompts/resources or SSE subscriptions.

Use the [release process](../reference/release-process.md) for version/contract
alignment, dependency/legal inventory verification, candidate quality gates and
the exact AMD64/ARM64 image scan/smoke/promotion checks. Capacity evidence uses
disclosed synthetic workloads and limits; qualify the actual deployment's
hardware, IdP/TLS, receiver permissions and backup/key custody separately.
