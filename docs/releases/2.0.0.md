# ThreatLens 2.0.0

This release adds team ownership, shared triage, reviewed report publication,
multiple AI providers, and durable processing/export recovery. It also changes
database deployment credentials and the default publication policy for new
reports. Read the upgrade requirements before replacing a 1.x installation.

## Main changes

- Named teams use group-backed membership and delegated management for shared
  views, investigations and triage. Shared watchlists support claims,
  assignments, due dates and visible escalation activity.
- Reports support draft, review, approval and publication. Approval is tied to
  the content and evidence revision; subsequent edits invalidate it. Report
  authoring, citations, library navigation and downloadable formatting have
  expanded regression coverage.
- AI settings support named providers, feature routing, model capabilities,
  request dialects and separate report token budgets. Durable execution
  ownership, bounded provider responses and request deadlines improve recovery
  without automatically replaying ambiguous provider calls.
- Statistics includes AI usage and reliability over time, provider/model and
  feature attribution, latency, token completeness, failures and backlog age.
  Charts include keyboard interaction and exact-data tables. Unknown token
  usage is disclosed rather than counted as zero.
- Processing worklists expose failures and selected-item recovery. Background
  exports use durable jobs and dedicated worker slots. Dispatch admission,
  retention progress and incremental history pruning bound recovery work.
- Organization workspace policies can provide or enforce navigation,
  dashboard and landing-page arrangements without granting feature access.
- Runtime database privileges are separated from migration and recovery roles.
  Containers have resource and writable-path restrictions; outbound operations
  and database waits have explicit budgets.

## Compatibility changes

| Existing behavior | Behavior in 2.0.0 | Required action |
| --- | --- | --- |
| One database identity may serve application, migrations and recovery. | Bundled Compose requires separate runtime and migration credentials; the database service retains the recovery administrator. | Complete the explicit offline role cutover below. Preserve initialized database credentials, encryption keys and volumes. |
| Newly generated reports can publish and deliver automatically. | New manual reports require editorial review before publication. New schedules default to requiring review unless their policy explicitly disables it. | Update automation and operator workflows to account for approval/publication. Set a schedule's review policy deliberately. |
| Existing stored reports and schedules use their legacy publication policy. | Migration preserves the legacy policy and historical reports. | Review schedules when adopting editorial governance; migration does not silently opt them into review. |
| Older workers consume earlier queues and do not understand team ownership or report editorial state. | Updated API and workers share the new ownership, execution and queue contracts. | Upgrade every API and worker together; do not perform a mixed-version rolling deployment. |
| Downgrades can remove newly introduced schema. | Downgrade guards reject removal when protected team ownership or editorial history would be lost. | Use the documented rollback procedure or restore the verified pre-upgrade backup. Do not bypass the guards. |

The application release number and API route version are separate. Existing
`/api/v1` routes remain; a structurally additive request schema does not imply
unchanged publication behavior for clients that omit the new schedule policy.

## Upgrade from 1.x

1. Back up and verify the currently working deployment. Retain its exact source
   or image reference, Compose configuration, environment and encryption keys
   in private storage. Do not recreate credentials for an initialized volume.
2. Complete [the offline database-role cutover](../pages/database-privileges.md#existing-installations-explicit-offline-cutover).
   Add the runtime/migration credentials while preserving the recovery
   administrator and database name. Use the migration service for schema
   changes; normal API/worker credentials intentionally cannot perform DDL.
3. Follow the stopped-writer requirements for
   [classification recovery](../reference/pipeline.md#classification-recovery-cutover)
   and [lifecycle queue cutover](../reference/configuration.md#lifecycle-queue-cutover).
   Stop all API, Beat and worker processes before migration. Classification
   migration scans retained article text, so allow an appropriate maintenance
   window for the installation's data volume.
4. Upgrade the API and all workers to the same release. The AI worker must
   consume `ai,ai-reports-v2,ai-reports-v3`; include the dedicated export worker
   and the maintenance/notification workers. Use the same image reference
   throughout the stack.
5. Check migration completion, API readiness, login, ingestion and processing
   freshness. Exercise a synthetic report's review/publication and a background
   export. Verify intended team access and workspace policy behavior.
6. Run a backup and disposable recovery drill using the upgraded deployment.
   See [database and recovery privileges](../pages/database-privileges.md) and
   [operations](../pages/operations.md).

Use the [release process](../reference/release-process.md) for version metadata,
generated API/dependency artifacts, exact image scans and release promotion.
The mutable `main` and `latest` tags can advance after a main-branch push passes
the publishing gates; use immutable release or commit references for a
controlled rollout.

## Operational limits

Teams supplement existing feature and evidence permissions; they do not provide
complete tenant isolation for every global feed, provider or integration.
Escalation currently creates application activity rather than an external on-call
notification. Automated browser/accessibility tests do not replace human
screen-reader evaluation. Citation checks establish reference integrity rather
than the truth of a model's claims.

Capacity measurements use bounded synthetic service workloads and disclosed
resource limits. They do not establish a universal supported deployment size or
live-provider quality guarantee. Compare measurements on intended hardware and
retain successful sample counts, queue recovery, database waits and memory
alongside latency. See the [capacity runbook](../reference/capacity-baseline.md).
